## 30 秒速览

Max 归约的缺陷比 plan.md 描述的更宽也更窄：**更宽**——最小复现只要两个元素，`[0, 1]` 会返回 0；**更窄**——只在 `columns.len() > 3` 时出现，3 列的实现是对的。机理是「一行把位置 i 与位置 G+i 配对，归约到 G 个输出就停，最后只取第 0 个」，于是返回值退化成「每 G 个位置取一个的同余类最大」。6 列、9 元素窗口下它恒等于 `max(x0,x2,x4,x6,x8)`，奇数下标全丢；0/1 穷举 512 例错 15 例。修复分两段（树形 → 显式 collapse 到单输出），并顺带**比原实现更省行**（6 列 9 元素：11 行 → 7 行）。

另外三件契约落成可审的补丁：PADV2 从「列表相邻 + 前面有 ReLU」升级为**按 tensor ID 的图级检查**（常量必须 -inf/0、生产者带 ReLU、输出唯一被 VALID MaxPool 消费、非图输出、填充对称且小于核）；元数据张量（paddings / -inf / axes）从运行时依赖移除并按数据依赖重算 `keep_tensors`；数值编码把「`-inf` 静默变成 INT64_MIN」变成加载前就拒绝。四个补丁都通过 `patch --dry-run`，但**一行 Rust 都没编译**。

## 2 问题 1：Max 归约漏输入

### 2.1 缺陷拆解（两个独立缺陷，不是一个）

`num_cols_per_op = 3`、`G = columns.len()/3`、`num_inputs_per_row = 2G`、`num_outputs_per_row = G`。
`op_row_region` 用 `inp.chunks(G)` 取前两块再 zip，所以**一行只把位置 `i` 与位置 `G+i` 配对**：

```
[a, b, c, d]  (G=2)  ->  [max(a,c), max(b,d)]
```

| 缺陷 | 位置 | 表现 |
|---|---|---|
| **D1 覆盖不全** | `forward` 的循环终止 + 末尾 `outputs[0]` | 归约到 `G` 个输出时 `len % num_inputs_per_row` 补齐后成为不动点，永远到不了 1；最后只取第 0 个 → 结果是某个「同余类」的最大值 |
| **D2 终止条件靠经验常数** | `num_iters = div_ceil + num_inputs_per_row` | 迭代次数是猜的，不是「直到剩 1 个」；多跑的那几轮只是重复同一不动点，白占行 |

D1 与 D2 相互独立：即使把 `num_iters` 调到任意大，`outputs` 仍停在 `G` 个，`outputs[0]` 仍是同余类最大。所以 plan.md 那句「增加循环次数也不能自动合并两个分组」是对的。

### 2.2 复刻证据（`scripts/p4a_max_model.py`，**对源码调度的 Python 复刻，不是运行 Rust**）

覆盖指纹 = 「把 1 放在该下标、其余取 0 时，函数返回值仍为 1」的下标集合：

| 列数 C | n | 覆盖下标 | 缺失 |
|---|---|---|---|
| 3 | 9 | `[0..8]` 全部 | — |
| 6 | 9 | `[0,2,4,6,8]` | `[1,3,5,7]` |
| 9 | 9 | `[0,3,6]` | `[1,2,4,5,7,8]` |
| 12 | 9 | `[0,4,8]` | 其余 6 个 |

两个立刻可用的强结论：

1. **C=3 完全正确**。缺陷被 `columns.len() > 3` 门控，而 converter 默认 `num_cols=6` —— 也就是说这个 bug 在默认配置下**必然生效**。
2. **最小反例只要 2 个元素**：`C=6, n=2, x=[0,1] → 返回 0`。不需要凑 9 元素窗口，P4-B 的最小复现可以做到极小。

0/1 穷举（全枚举，非抽样）：

| C | n=2 | n=3 | n=4 | n=6 | n=9 | n=10 |
|---|---|---|---|---|---|---|
| 3 | 0/4 | 0/8 | 0/16 | 0/64 | 0/512 | 0/1024 |
| 6 | 1/4 | 1/8 | 3/16 | 7/64 | **15/512** | 31/1024 |
| 9 | 1/4 | 3/8 | 3/16 | 15/64 | **63/512** | 63/1024 |
| 12 | 1/4 | 3/8 | 7/16 | 15/64 | **63/512** | 127/1024 |

plan.md 指定的反例（9 元素、零基 `x1=1`、其余 0）复现：C=3 返回 1（对），C=6/9/12 均返回 0（反例成立）。末端两个分组正是 `[0, 1]`，与 plan.md 的描述逐字一致。

对 MaxPool2D 的实际影响：窗口长度不是常数——内部 9、边缘 6、角 4（`max_pool_2d.rs` 的 `splat` 只在越界时跳过）。这三种长度在 C=6 下全部踩中 D1（n=4 错 3/16、n=6 错 7/64、n=9 错 15/512），所以**不是只有内部窗口错**。

### 2.3 候选修复（`patches/max_reduce_fix.rs`）

```
阶段一（树形）：while L > G { 补齐到 2G 的倍数（补 cur[0]）; 一次行归约 }   L -> ceil(L/(2G))*G
阶段二（collapse）：while L > 1 { 两两 max2; }                              L -> ceil(L/2)
单元素直接返回；空输入 / 列数非 3 倍数 / 列数 < 3 -> Err 或构造期 assert
```

`max2(a,b)` 的关键是**把两个操作数放进同一组**：一行长度为 `2G`，位置 `0` 放 `a`、位置 `G` 放 `b`、其余填 `a` → 第 0 组 = `(a,b)` → `out[0] = max(a,b)`；其余组 `(a,a)` 输出 `a`，丢弃。
（不能简单地把 `[a,b]` 补齐后送进行归约——那正是原实现丢一半输入的机理：`a`、`b` 会落在**不同组**的同一侧，永远不被比较。）

**正确性论证**（对应补丁头注释 I1–I4）：

- I1 不变式：`cur` 每个 cell 都是「原始输入某个非空子集的最大值」。因此 `max(cur) ≤ 全窗口最大`，且全集最大一定被某个 cell 取到 → `max(cur) = 全窗口最大`。
- I2 补齐只复制 `cur[0]`，是集合内元素：既不引入更大的值，也不删除任何原元素。
- I3 一次行归约把 2G 个位置按 `(i, G+i)` 两两配对，**覆盖全部 2G 个输入且不重不漏**，输出仍是子集最大 → 集合最大不变。
- I4 `max2(a,b)` 精确等于 `max(a,b)`，长度减半。
- 终止：阶段一在 `L > G` 时 `ceil(L/(2G))*G < L`；阶段二 `ceil(L/2) < L`（`L ≥ 2`）。两者都严格下降。

**顺带更省行**（每次 `MaxChip::forward` 产生的 gadget 行数）：

| C | n | 原实现 | 修复后 |
|---|---|---|---|
| 6 | 4 | 6 | 2 |
| 6 | 6 | 8 | 4 |
| 6 | 9 | 11 | 7 |
| 3 | 9 | 15 | 11 |
| 12 | 9 | 12 | 6 |

原因是 D2 那 `+ num_inputs_per_row` 的额外迭代全在不动点上空转。**这不是性能优化，是缺陷修复的副产品**；不能拿它去宣称 prove 时间改善。

### 2.4 修复的适用域与拒绝契约

| 契约 | 处理 |
|---|---|
| `columns.len() % 3 != 0` | 构造期 `assert_eq!`（原实现用整除**静默截断**，例如 7 列被当成 2 组、第 7 列永不使用） |
| `columns.len() < 3` | 构造期 `assert!` |
| 输入为空 | `Err(Error::Synthesis)`（原实现在 `inputs[0]` 处 panic） |
| 单元素 | 直接返回，占 0 行（原实现在 G≥2 时也要跑 2 行） |
| 任意长度 ≥1、任意 3 的倍数且 ≥3 的列数 | 支持（已验证 1..10 × {3,6,9,12}） |

> 未编译点：`Error::Synthesis` 这个变体名需要在 P4-B 首次编译时确认；若该 halo2 rev 的 `plonk::Error` 没有这个 unit variant，改为已知变体即可，不影响算法。

## 3 问题 2 + 3：PADV2 图级保护与元数据依赖清理

### 3.1 原状态的两个具体缺口

1. **转换侧**：`converter.py` 完全没有 `PADV2` 分支（P3 实测停在 `layer 2: 60, PADV2`）。P3 的探针补丁只是「当 PAD 处理」，**没有做任何图检查**，因此 -inf → 0 的降级是无条件发生的。
2. **Rust 侧**：`PadChip` 硬编码 `constants.get(&0)`，也就是填充值恒为 0；`dag.forward` 在调用层之前先把**全部** `inp_idxes` 从 `tensor_map` 里 clone 出来。而 `tensor_map_to_vec` 会用 `smallest_tensor` **静默填补索引空洞** —— 所以「只从 tensors 里删掉 idx1」不仅不够，还会让漏改的层拿到一个形状可能恰好对得上的错误张量。

### 3.2 候选契约（`patches/converter_p4a.py`，12 处编辑）

**图索引**：按 tensor ID 建 `producer[t]` 与 `consumers[t] = [(op_idx, input_pos)]`，不再依赖算子列表顺序或「相邻」这种脆弱假设。

**PADV2 检查（任一不满足即拒绝，不静默降级）**：

| # | 条件 | 依据 |
|---|---|---|
| P1 | 常量是单元素，且为 `-inf` 或 `0` | 其它常量（如 -3.0）无法用 0 填充等价 |
| P2 | 常量为 `-inf` 时，数据输入的**生产者 fused activation 必须是 RELU** | 0 填充与 -inf 填充等价 ⟺ `max(x) ≥ 0`；ReLU 给的就是这个保证 |
| P3 | Pad 输出**恰好 1 个**消费者，且是 `pad=VALID`、无 fused activation 的 `MAX_POOL_2D` | Pad 输出若还被别的算子观察，降级就不只影响池化 |
| P4 | Pad 输出**不是图输出** | 公开张量不能被悄悄改值 |
| P5 | 填充在 H/W 上对称，每侧 `< 核尺寸`；batch/channel 轴无填充 | 对称 = PyTorch 语义；`pad ≥ kernel` 会出现「整窗都是填充」，此时 0 与 -inf 给出不同结果 |

P5 是 plan.md 说的「每个有效池化窗口非空」的可判定形式。本图是 `pad=1, kernel=3`，满足。

**元数据依赖清理**：只对**本图实际出现**的算子登记元数据位置，并额外要求「该 tensor 的全部消费者都只在元数据位置引用它」才允许移除：

```python
METADATA_INPUT_POS = {
  'PAD':   [1],      # paddings
  'PADV2': [1, 2],   # paddings, constant
  'MEAN':  [1],      # axes
}
```

然后按**过滤后的** `inp_idxes` 重算 `keep_tensors`（不是只从 `tensors` 里删条目）。本图预期被移除的是：PADV2 的 paddings（`[4,2]`）与 -inf 常量（`[1]`）、4 个 PAD 的 paddings。PADV2 的依赖从 `[48,45,1] → [49]` 变成 `[48] → [49]`，tensor ID 保留不变。

> 没有登记 `RESHAPE` / `TRANSPOSE` / `SLICE` / `SPLIT` 等，虽然它们同样是元数据驱动。理由：本图没有这些算子，登记了也无法验证，属于无证据的扩大改动面。新增算子必须逐一核对对应 `Layer::forward` 到底读了哪几个 tensor。

### 3.3 Rust 侧的配套断言（`patches/pad_contract.rs`）

恢复注释掉的 `assert_eq!(tensors.len(), 1)`：依赖清理漏改时**立即失败**，而不是默默用 `tensors[0]`。原注释 `// FIXME: the pad from tflite is actually two, but mine is one` 正好说明这就是当年绕过去的地方。

### 3.4 禁止填洞（`patches/model_numeric_contract.rs` N4）

`tensor_map_to_vec` 改为：先算出 `0..=max_key` 里缺哪些键，非空即 panic 并打印缺失列表。这样「删了张量但没改 `inp_idxes`」会在加载阶段炸出来，而不是拿到 `smallest_tensor`。

**风险必须写明**：如果既有 MNIST 产物的索引本来就不连续（当年的填洞可能就是为此），这个改动会直接失败。所以 P4-B 的第一步是拿 MNIST 既有 msgpack 验证索引连续性，再决定是否启用。

## 4 问题 4：数值边界契约

### 4.1 编码区间：`to_field` 只对 `[-2^31, 2^31-1]` 精确

`model.rs:297-302` 是 `F::from((x + 2^31) as u64) - F::from(2^31)`：

| x 区间 | 实际行为 |
|---|---|
| `[-2^31, 2^31-1]` | `x + 2^31 ∈ [0, 2^32-1]`，`as u64` 精确，减回去等于 `x` ✅ |
| `x < -2^31` | `x + 2^31` 为负 → `as u64` 补码回绕 → 编码成 **`x + 2^64`**（一个巨大正元素），静默改义 ❌ |
| `x > 2^31-1` | `x + 2^31` 可能溢出 i64（debug panic / release 回绕）❌ |

`-inf → INT64_MIN = -2^63` 正好落在第二行，所以 P3 里那个死常量如果在 Rust 侧被赋值，会变成 `2^64 - 2^63 = 2^63` 量级的正元素。**P3 说它「对下游没有影响」只对 TFLite/msgpack 层成立；一旦进 Rust 就不是。**

### 4.2 由编码区间反推的两条硬约束

| 约束 | 推导 | 结论 |
|---|---|---|
| `k ≤ 32` | `min_val = -(2^(k-1))` 必须 ≥ `-2^31` | k=33 起 `min_val` 越界 |
| `sf ≤ 2^22` | `shift_min_val = -(sf² · 2^17)` 必须不溢出 i64，即 `sf² · 2^18 ≤ 2^63-1` | sf=2^22 → 2^62 ✅；sf=2^23 → 2^64 ❌ |

第二条尤其要注意：原代码 `-(config.global_sf * config.global_sf * (1 << 17))` 是 i64 乘法，release 下溢出**不报错**。补丁改用 `i128::checked_mul`。

### 4.3 MaxChip 自己的数值域（比编码区间宽，故不构成瓶颈）

`convert_to_u64(&(v + 2^49))` 要求 `v + 2^49 ∈ [0, 2^64)`（`big_digits.len()==2` 会 panic），即

```
-2^49 ≤ v < 2^64 - 2^49        （sf = 2^16 时；一般地 v < 2^64 - sf²·2^17）
```

配合 4.1 的 `[-2^31, 2^31-1]`，**编码区间才是绑定约束**。这条写下来是为了防止「以为 Max 能处理任意大数」的误判。

### 4.4 舍入规则

`converter.py` 用 `(x * sf).round()` —— numpy 的 `round` 是 **half-to-even**（银行家舍入）。补丁改成显式 `round_half_away_from_zero`。理由不是「更准」，而是**规则必须写死并被两边知道**：定点误差预登记时，参考实现的舍入方式必须与 Rust 侧一致，否则首个分歧会被误判成算子错误。

### 4.5 尚未闭合的部分（必须在 P4-B 才能做）

- lookup 表的**差值域**到底覆盖 `[0, 2^k]` 还是更窄：本批没有逐表核对 `input_lookup` 的填充方式，列为 P4-B 第一项。
- 各 gadget 自己的 `min_val/max_val` 派生域（ReLU / Div / BiasDiv 各不相同）：plan.md 已要求「不能对所有张量机械套一个区间」，本批只给出框架与 Max 一条。

## 6 给 P4-B 的测试矩阵、预期开销与停止条件

### 6.1 编译期（先做，几分钟）

1. `cargo check --locked` 只编 `src`，确认 4 个补丁的类型/借用/`Error::Synthesis` 变体。
2. 先单独应用 `max_reduce_fix` 编译；再叠加另三个。**分开编译**才能在失败时定位到具体补丁。

### 6.2 Max（最小、最高优先级）

| 用例 | 期望 |
|---|---|
| `n=2, [0,1]` | 1（**原实现返回 0，最小复现**） |
| `n=9, x1=1 其余 0` | 1（原实现 0） |
| 9 元素逐位置取最大（9 个用例） | 各自等于该位置值 |
| 并列最大（多处相同最大值） | 等于该值 |
| 全 0 / 全同值 / 合法负值（如全 -3） | 正确 |
| 合法负值 + 单点最大为负（全部为负的窗口） | 正确（`neg_const` 输入会造出全负池化窗口，必须单独覆盖） |
| 长度 4 / 6 / 9（角/边/内部窗口） | 正确 |
| 非整行长度（如 5、7）、奇数长度 | 正确 |
| `columns ∈ {3,6,9,12}` 全部重跑 | 正确（D1 只在 >3 出现，3 列是对照组） |
| 空输入 | 返回 `Err`，不 panic |
| 约束侧：每行 `(in1-out)(in2-out)=0` 与两条差值 lookup 同时成立 | MockProver 通过 |

### 6.3 Pad→Max 与依赖清理

| 用例 | 期望 |
|---|---|
| 本图（conv1+ReLU → PADV2(-inf) → MaxPool） | 转换通过，证据 JSON 落盘 |
| 生产者不是 ReLU（人为改 activation） | **拒绝** |
| PADV2 常量改成 -3.0 | **拒绝** |
| Pad 输出多接一个消费者 | **拒绝** |
| Pad 输出设为图输出 | **拒绝** |
| `pad=2, kernel=3`（整窗可为填充） | **拒绝** |
| 删除 pads 后漏改某层 `inp_idxes` | N4 立即 panic 并打印缺失索引 |
| MNIST 既有 msgpack 在 N4 下加载 | 索引连续 → 通过；不连续 → 说明填洞在用，需回退 N4 或修数据 |

### 6.4 数值边界

| 用例 | 期望 |
|---|---|
| `x = -2^31` / `2^31-1` | 编码精确 |
| `x = -2^31-1` / `2^31` | 拒绝并报 tensor id + 下标 |
| `INT64_MIN` | 拒绝（这正是 -inf 的产物） |
| `NaN` / `±Inf` | converter 侧就拒绝（`_quantize_checked`） |
| `k=32` / `k=33` | 通过 / 拒绝 |
| `sf=2^22` / `sf=2^23` | 通过 / 拒绝 |

### 6.5 预期开销与停止条件

| 项 | 估计 |
|---|---|
| `cargo check` | 分钟级（依赖已编译过） |
| Max 单 gadget 测试 | 每例毫秒级，但 **configure 会按 k 建表**，须先固定小 k |
| Pad/Max 组合测试 | 同上，窗口总数 = 输出尺寸，用 8×8 输入即可 |
| 停止条件 | 任一用例与参考不符即停；宁可留着失败原件，也不调参掩盖 |

> **特别注意**：即使是「只测一个 gadget」的 MockProver，也会走 `configure`，而 `configure` 会按 `2^k` 建 HashMap 与 lookup（plan.md §2.7.2 第 5 条）。所以 P4-B 必须显式指定小 k 并先算 configure 的开销，不能因为「输入是 8×8」就认为便宜。

## 8 复现命令（本批全部是本地静态操作）

```bash
# 1) Max 复刻与反例枚举（纯 Python，不接触 Rust/远端）
python scripts/p4a_max_model.py

# 2) 重新生成四个补丁（幂等；锚点不唯一会 assert 失败而不是盲改）
python scripts/p4a_make_converter_patch.py
python scripts/p4a_make_model_patch.py
python scripts/p4a_make_pad_patch.py

# 3) Max 补丁是直接写的固定文件，diff 由 diff 生成
diff -u zkml-main/src/gadgets/max.rs patches/max_reduce_fix.rs > patches/max_reduce_fix.diff

# 4) 应用性检查（在副本上，不碰仓库文件）
cp zkml-main/src/gadgets/max.rs /tmp/m.rs && (cd /tmp && patch --dry-run -p0 m.rs < .../max_reduce_fix.diff)

# 5) 重算 manifest 并与落盘文件比对（--check 只读，不一致退出码 1）
python scripts/p4a_manifest.py --check
```
