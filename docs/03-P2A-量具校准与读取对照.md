## 0. 一句话结论

旧结论"SRS 慢在逐点解码"**是错的**。同一 `ParamsKZG::read`、同一 `SerdeFormat`，只把未缓冲 `File` 换成 1 MiB `BufReader`，SRS 段从 **187.8 ms 掉到 6.18 ms（约 30×）**；完整请求从 **211.7 ms 掉到 28.5 ms（约 7.4×）**。慢的是 **524,288 次 8 字节 `read_exact` 系统调用**，不是点解码。

## 1. 量具 v2.1（`scripts/runwrap.py`）

旧 `measure.py` 的缺陷（`plan.md` §2.5 已列）：20 ms 轮询检测退出、RSS 采样漏峰、affinity 取父进程、子进程失败仍返回 0。

新量具的计时边界：

```text
打开日志/采样准备（不计时）
        ↓
t0 = monotonic()                ← 紧邻 spawn 之前
Popen(cmd, stdin=DEVNULL, stdout=日志, stderr=日志, cwd=样本目录)
启动监视线程（独立线程，只采 VmHWM / Cpus_allowed_list / 线程数 / cgroup）
os.wait4(pid, 0)                ← 唯一的回收路径，不与 Popen.poll/wait 竞争
t1 = monotonic()                ← wait4 返回后立即取
stop.set(); th.join()           ← 在 t1 之后，不会推迟退出检测
```

返回码：`signal = WTERMSIG`，`code = 128+signal`（无信号时用 `waitstatus_to_exitcode`），**原始 wait status 一并保留**；普通失败让包装器失败，负例由调用方判断预期。

### 自测（`scripts/p2a_selftest.py`，输出 `runs/p2a-calib1/logs/selftest-v2/`）

| 用例 | 判据 | 实测 | 结果 |
|---|---|---|---|
| 快速成功 `/bin/true` | < 30 ms | **1.786 ms** | pass |
| 可控时长 `sleep 0.300` | 0.29–0.45 s | 0.3027 s | pass |
| 非零退出 `exit 7` | code=7 且 signal=0 | 7 | pass |
| 信号终止 `kill -TERM $$` | signal=15、code=143 | 15 / 143 | pass |
| 10× `/bin/true` 重复性 | spread < 25 ms | 1.581–1.725 ms，max−min = **0.144 ms** | pass |
| 绑核采样 `taskset -c 3 sleep 0.05` | 末次观测 = "3" | 观测到 `["0-127","3"]`，末值 **"3"** | pass |

`all_pass: true`。

- 旧量具对 `/bin/true` 的下限是 ≥20 ms，新量具 **1.6 ms**，周期性检测滞后消失。
- 绑核那条用例是补上来的：第一版只采一次样本，而 `taskset` 是"先设掩码再 exec"，第一样本必然读到 `0-127`。实测确认了这个坑（`["0-127","3"]`），已改为全程采样并记末次值。

### 归因纠正（重要）

| 旧说法 | 实测 |
|---|---|
| "读 4 MB 只要 3.2 ms，其余 182 ms 全是逐点解码" | 错。**换成缓冲读就把 182 ms 消掉了**，逐点解码（含 G1 的 on-curve/子群检查）剩下 **≤6.18 ms** |
| "瓶颈在逐点解码校验，不在 I/O" | 错。瓶颈在**未缓冲 `File` 的 524,288 次 8 字节 `read_exact` 系统调用**；`ParamsKZG::read` 对每个 32 B 坐标分 4 次 8 B 读，一个 G1 点 8 次，2×2^15 点合计 524,288 次 |
| "k=15 的 SRS 段 = 185.5 ms，按 2^k 线性外推 k=28 ≈ 25 min" | 这条外推的基数错了，必须作废重算（见下） |

按 `plan.md` §2.5 的要求，这只是**把解释改对**，不是宣布"完成优化"：A/B/C 三组走的是同一个 `ParamsKZG::read`、同一个 `SerdeFormat`、同一个 transcript 和同一套检查，没有改成 `Unchecked`，也没有取消任何校验。

### 重算后的规模外推（**仍然是估算，未实测**）

以 B 组的 `ParamsKZG::read` = 6.18 ms（k=15，2×2^15 点）为基数，按点数线性放大：

| k | 参数文件 | 仅 `ParamsKZG::read`（外推） | 旧外推（已作废） |
|---|---|---|---|
| 15（实测） | 4.2 MB | **6.18 ms** | 186 ms |
| 20 | 134 MB | ~198 ms | ~5.9 s |
| 24 | 2.1 GB | ~3.2 s | ~95 s |
| 28 | 34.4 GB | ~51 s | ~25 min |

k≥24 时文件读取本身（2.1 GB / 34.4 GB）会成为新的下限，上表只算了"按点数放大的解码成本"，没算把几十 GB 从磁盘搬进内存的时间。**这张表不能用来宣布目标可达，也不能用来宣布目标不可达。**

## 3. 负向与证据（`scripts/p2a_neg.py`，输出 `runs/p2a-calib1/neg_report.json`）

### 3.1 先解决一个方法论问题：proof 元素是点还是标量

本依赖集里 `read_point` 走 `C::Repr`，而 halo2curves 0.3.2 的 G1 **compressed 编码就是 32 字节** —— 所以**不能按长度区分点与标量**。第一版追踪输出把 32 B 一律标成 "scalar"，那是假声明，已删除标签，只保留偏移与长度。

改用**解码器自身的行为**分类：把第 i 个 32 B 元素整体替换为 32 个零字节（这是域元素 0 的合法编码），看拒绝发生在哪一步。

- 37 个元素（索引 0–35、103）在该元素处报 `Transcript(... 'invalid point encoding in proof')`，读入在第 i+1 个元素处停止 ⇒ 零字节不是合法点编码 ⇒ 这些是**曲线点**。
- 68 个元素（索引 36–102、104）接受零字节、**整份 proof 仍解码完（105 次读 / 3360 B）**、随后被校验拒绝 ⇒ transcript 只有 `read_point` / `read_scalar` 两条读路径，既然零字节已被证明不是合法点编码，这些必定走 `read_scalar` ⇒ 这些是**域元素**。
- 歧义项：0 个。

这个分类同时给出"整份 proof 到底读了多少"的基线：**105 次 `read_exact`、每次 32 B、共 3360 B**。

### 3.2 用例与结果（三组均跑 `--diag --trace-reads`）

| 用例 | 改动 | 退出码 | 读完？ | 拒绝阶段 | 底层错误 |
|---|---|---|---|---|---|
| 正例 | 无 | 0 | 105 / 3360 | 接受 | `Ok` |
| public value 换值 | 第 0 个元素低位翻转（仍是合法规范域元素） | 2 | 105 / 3360 | **全解码后校验拒绝** | `ConstraintSystemFailure` |
| public value 非规范 | 第 0 个元素置 `0xff×32` | 101 | — | **加载阶段** | panic（域元素解码失败） |
| proof 点元素换点 | 元素 0 ← 元素 1 的 32 字节（**合法点编码**，但不是被承诺的那个点） | 2 | 105 / 3360 | **全解码后校验拒绝** | `ConstraintSystemFailure` |
| proof 点元素非法编码 | 元素 0 ← `0xff×32` | 2 | 1 / 32 | **解码失败**（第 1 个元素处） | `Transcript(... 'invalid point encoding in proof')` |
| proof 域元素换值 | 元素 36 低位翻转（另一个合法规范域元素） | 2 | 105 / 3360 | **全解码后校验拒绝** | `ConstraintSystemFailure` |
| proof 截断 32 B | 去掉最后 32 字节 | 2 | 105 次尝试 / 只到 3328 B | **解码未完成** | `Opening` |
| SRS 缺失 | 参数目录为空 | 101 | — | **加载阶段** | panic；目录前后均为空，**没有生成新 SRS** |
| SRS 截断 | 只留前 4096 B | 101 | — | **加载阶段** | panic；规范 SRS 摘要不变 |
| VK 截断 | 只留前 1024 B | 101 | — | **加载阶段** | panic；规范 VK 摘要不变 |

三个读模式（`file` / `bufreader` / `memory`）在上述每个用例上的**接受/拒绝结论完全一致**，这正是 `plan.md` 要求的加载等价性。

### 3.3 截断用例暴露的一个陷阱

截断 32 B 时底层错误是 **`Opening`**，而不是 transcript 类错误 —— 因为 SHPLONK 把自己尾部两点读取失败映射成了 `Opening`。所以**不能只靠错误名判断"是解码失败还是校验失败"**，必须结合"是否读完"：

```text
stage = 加载失败(panic)        若进程在构造验证对象前就终止
      = 解码失败              若消费字节数 < 3360（无论错误名叫什么）
      = 校验拒绝              若 105 次读、3360 B 全部消费完仍被拒
```

### 3.4 因此可以说与不可以说

可以说：
- 篡改一个**合法编码**的 proof 点元素或域元素后，proof **被完整解码**（105 次读、3360 B 全部消费），随后被密码学校验拒绝；
- 修改一个规范域元素形式的 public value，同样在全解码后被拒绝；
- 截断、非法点编码、非规范域元素、缺 SRS、截断 SRS/VK 都在**加载/解码阶段**就快速失败，且**没有触发任何 fallback setup 或参数重生成**。

不可以说：
- 不能说这次证明了完整的**可靠性（soundness）**；单个诚实输入的少量负例不是可靠性证明；
- 不能说"proof 元素 104 一定是标量"之外的更多结构结论 —— 本文只报告解码器判定出的 37 点 / 68 域元素这一事实，不据此声称完整的 proof 布局语义；
- 不能说目标 ResNet-18 的性质。

## 4. 绑核、线程与资源

| 组 | 子进程末次 `Cpus_allowed_list` | 线程数 | `ru_maxrss` 中位 |
|---|---|---|---|
| O | `0` | 外层峰值 2（上游不报内部值） | 12,256 KB |
| A | `0` | 外层峰值 2；插桩自报 `threads_at_end = 2` | 12,248 KB |
| B | `0` | 同上 | 12,266 KB |
| C | `0` | 同上 | 15,922 KB（多 4 MB 缓冲） |

- 绑核证据对 O 组来自**外层读目标 PID 的 `/proc/<pid>/status` 末次观测**，不是父脚本 affinity；对 A/B/C 另有程序内 `affinity_start` / `affinity_end` 自报，全部为 `"0"`。
- `threads_at_end = 2` = 主线程 + 1 个 Rayon worker，与 `RAYON_NUM_THREADS=1` 一致。
- `ru_maxrss` 是 `wait4` 给出的**被回收子进程自身**峰值，不含子孙并发内存；不把它当进程树总量。

## 5. 本阶段结论

1. **量具已校准**：`/bin/true` 1.6 ms 级别、无 20 ms 量化、外-内差稳定 6–7 ms、绑核与线程数可追溯、退出码/信号不吞。
2. **SRS 慢的归因已被实测推翻并改对**：不是点解码，是未缓冲 `File` 的 52 万次小 `read_exact`。同一 `ParamsKZG::read` 加缓冲即 187.8 → 6.18 ms。
3. **完整请求从 213.4 ms 降到 28.5 ms（约 7.5×）**，k=15 下距离 1000 ms 预算很宽裕，但这**只说明 MNIST。**

   > **不能**据此说目标 ResNet-18 一定达标。
4. **新增的关键信息（影响 P2B 决策）**：既然后处理参数加载只剩 6.2 ms，"验证方专用轻量参数（只读 `g2`/`s_g2`）"的理论收益上限从 185 ms 掉到 **最多 6.2 ms**。P2B 的性价比已大幅下降，是否还做需要重新评估 —— 但它也不是零收益，且与规模强相关（k 越大，6.2 ms 也越大）。
5. **负向证据已可分类**：全解码后被密码学拒绝 vs 加载/解码阶段失败，两类都有实例，且不依赖统一 panic 文案。

## 6. 未做 / 局限

- 单容器、共享宿主（采样期间 load average ≈ 10，见 `abc/summary.json` 的 `loadavg_*`），不是独占 CPU；未做温度/NUMA 控制。
- 每组 10 个样本，p95 只是样本描述，不能当尾延迟保证。
- 未做 16 线程辅助对照（`plan.md` 列为本批非必需，如另做必须单列）。
- O 组内部阶段不可得（上游 binary 无插桩），只报外层 wall，未用插桩版或插值填补。
- 未验证任何 k>15 的情况，所有规模数字都是估算。
- 未改动电路、协议、transcript、参数与密钥格式；新增代码只做插桩与读取方式对照。
